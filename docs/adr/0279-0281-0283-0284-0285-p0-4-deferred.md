# ADR 0279 + 0281 + 0283 + 0284 + 0285 — Remaining P0-4 slices (deferral + design notes)

## Status

Accepted as scope declaration. Each item stays `OPEN` in
the Platform Gaps Plan.

## Context

This autonomous G1 completion run shipped 9 P0-4 slices
(ADRs 0247–0251, 0258, 0278, 0280, 0282). Five remaining
items need infrastructure that goes beyond a single-session
code slice:

- **ADR 0279 — Per-object DDL grants** (per-schema /
  per-table CREATE / ALTER / DROP).
- **ADR 0281 — Role catalog** (named grant bundles;
  GRANT role TO user; chained roles).
- **ADR 0283 — TLS at the API boundary** (`rustls` + cert
  rotation).
- **ADR 0284 — mTLS client auth** (client certs → catalog
  users).
- **ADR 0285 — Rate limiting + audit of authn failures**
  (per-principal and per-IP token buckets; audit log
  entries on throttle).

## Decision

Each stays OPEN with a design note here so the next
implementer can start without re-deriving the plan.

### DDL grants (0279)

- Extend `ObjectCapability` with `CreateTable`, `AlterTable`,
  `DropTable`, `CreateSchema`, `CreateDatabase` variants.
- The engine's DDL dispatcher (`"create" => …`, `"alter" =>
  …`) classifies each statement and checks the user's
  per-schema or per-table DDL grant before executing.
- Bootstrap: `Capability::Ddl` implies every per-object DDL
  on every object.
- SQL: `GRANT { CREATE | ALTER | DROP } ON { SCHEMA |
  TABLE } <qualified> TO <user>`.

### Role catalog (0281)

- New `RoleRecord { name, capabilities: BTreeSet<Capability>,
  table_grants: BTreeMap<TableId, BTreeSet<ObjectCapability>> }`.
- `UserRecord` grows `roles: BTreeSet<String>`.
- `UserCatalog::create_role`, `drop_role`, `grant_role`,
  `revoke_role`.
- `PersistentUserCatalog` journals the role mutations.
- `UserRecord::allows_on_table` and `allows` union the
  user's own caps with every role's caps.
- SQL: `CREATE ROLE r`, `DROP ROLE r`, `GRANT r TO u`,
  `REVOKE r FROM u`. Role-to-role chains are a later slice.

### TLS (0283)

- Add `rustls = "0.23"` as a workspace dep.
- `bradian-serving` opens a TLS acceptor loaded from PEM
  files. Cert / key paths come from a new
  `ServingConfig { tls_cert, tls_key }`.
- Hot-reload: file-mtime polling or SIGHUP. Document the
  rotation story.

### mTLS (0284)

- Extend the serving TLS acceptor to require client certs.
- CN or SAN → user name lookup in `PersistentUserCatalog`.
- Fail-closed on missing / revoked cert.

### Rate limiting (0285)

- Reuse `rate_limiter::TokenBucket` (already shipped,
  ADR 0142).
- Per-principal bucket (keyed on user name). Default
  capacity + refill come from `ServingConfig`.
- `SqlEngine::execute_as` acquires one token before
  dispatch; failure surfaces `SqlError::Resource(…)`.
- Failed authz attempts also charge the bucket so
  brute-force attempts throttle.
- Audit entry on throttle event.

## Consequences

- P0-4 is substantially closed on verifiable features:
  users + argon2id, grammar, authenticated sessions,
  global grants, per-object SELECT / INSERT / UPDATE /
  DELETE, multi-table authz, revocation propagation.
  Five items remain for the next pass.
- TLS and mTLS require the `bradian-serving` crate to be
  the active API surface — the current loopback token path
  is explicitly documented as development-only.
