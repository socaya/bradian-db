# G6 exit evidence — DHIS2 Aggregate, Event and Tracker analytics

## Summary

DAP compiles and executes the three DHIS2 analytical families:

1. **Aggregate program analytics** — data value facts rolled up across period and org-unit
   dimensions according to each data element's `aggregationType`.
2. **Classic Indicators** — `(numerator, denominator, factor)` formulas with SQL null
   propagation and divide-by-zero → NULL.
3. **Program Indicators** for Event and Tracker programs — expression evaluated per event
   or per enrollment, then aggregated with the chosen DHIS2 aggregation type.

A shared expression grammar backs all three paths. Unsupported constructs reject at compile
time with a diagnostic (spec §6.1).

## Known limitations (deferred items)

1. **`d2:` function namespace** (`d2:yearsBetween`, `d2:monthsBetween`, `d2:daysBetween`,
   `d2:relationshipCount`, `d2:condition`, `d2:oizp`, `d2:hasValue`, `d2:zpvc`, `d2:count`,
   `d2:countIfValue`). The lexer rejects explicitly so no silent approximation can slip in.
2. **Period-offset modifiers** (`#{DE}.periodOffset(-1)`, `*.averagePerPeriodOffset`).
   Reserved for the analytical window operators.
3. **Reporting-rate variables** on datasets (`#{dsUID.REPORTING_RATE}` and friends). These
   need the dataset-completion engine.
4. **Aggregation types LAST / LAST_IN_PERIOD / STDDEV / VARIANCE**. Aggregate-side work.
5. **PI aggregation type `CUSTOM`**. Program Indicator metadata permits a user-defined
   aggregation expression; the engine rejects at eval time.
6. **Relationship analytics** (DHI-004): relationship-type cardinality + bidirectional
   joins.
7. **Program rules / assigned data elements**. Program rules can generate values that
   analytics must observe; the current ingestion path assumes the generated value has
   already been persisted.
8. **Dimensional disaggregation by option sets** inside event analytics (`option_set.code`).
   The engine stores option combos and option sets but does not yet route them as event-
   level grouping columns.
9. **Assigned user, event due date, event completion date filters.** Facts carry these;
   DSL-level ergonomics is tracked for API-002.
10. **Program indicators with analytics type `EVENT` targeting Tracker programs** should
    filter to events whose enrollment matches the program; this is handled correctly today
    (event's `program` field), but the catalog does not yet validate the PI's declared
    analytics type against the program type.

## Next-step plan (next iteration)

Priority ordering, with the exit evidence each step should carry:

1. **DHI: `d2:` function namespace.** Implement `d2:yearsBetween`, `d2:monthsBetween`,
   `d2:daysBetween`, `d2:hasValue`, `d2:condition`, `d2:oizp`, `d2:zpvc`, `d2:count`,
   `d2:countIfValue`. Each function gets at least one DHIS2 reference-output parity
   fixture under `fixtures/dhis2/`. Exit: `cargo test -p dap-dhis2 d2_functions`.
2. **Aggregate DHI: LAST / LAST_IN_PERIOD / STDDEV / VARIANCE.** Introduce a watermark-
   aware "last-of-group" combinator (two-pass or Welford-driven), tie-break by event
   time then ingest LSN. Exit: parity fixtures for each new aggregation type.
3. **Period offsets.** Parse `#{DE}.periodOffset(-1)` as an AST node that captures the
   shift; the enrollment / aggregate resolver evaluates against a period-shifted
   coordinate set. Exit: cohort-analytics fixture covering one-year lagged indicator.
4. **Reporting rates** (`#{dsUID.REPORTING_RATE}`, `#{dsUID.EXPECTED_REPORTS}`,
   `#{dsUID.ACTUAL_REPORTS}`). Depends on the dataset-completion engine (new fact table
   `(dataset, OU, period) → (expected, actual, completed, completion_date)`); the storage
   layer already supports multi-table partitions. Exit: completeness indicator parity.
5. **Program rules side-effect analytics.** Rules generate derived values; the ingester
   must receive them as separate canonical changes. Document the flow; add quarantine +
   provenance tagging for rule-generated rows. Exit: rule-driven DE flows through the
   ingest → aggregate PI pipeline with the same parity fixture.
6. **Relationship analytics (DHI-004).** New relationship fact table, bidirectional join
   semantics, `d2:relationshipCount` function. Exit: a cohort query that counts related
   events across a relationship type.
7. **Program indicator CUSTOM aggregation.** User-defined aggregation expression evaluated
   per enrollment-grain result; validate referential safety (no `#{DE}` recursion). Exit:
   two public DHIS2 custom-aggregation fixtures.
8. **Planner integration.** Expose event- and enrollment-grain queries through the DSL +
   HTTP API (today the HTTP surface only serves aggregate queries). Carry provenance per
   analytics type. Exit: end-to-end test: enrollment PI reaches via HTTP query, oracle
   parity passes.
9. **Materialized views for PI results.** Register a `MaterializedView` with the computed
   PI value per `(OU, period)` cell; wire catalog lineage so a change to the underlying
   DE invalidates the view. Exit: MV refresh benchmark for a 100k enrollment workload.
10. **DHIS2 metadata ingest.** Build an adapter that pulls the full metadata bundle
    (data elements, category combos, programs, program stages, program indicators,
    indicators, org units, relationships, option sets) from DHIS2's `/api/metadata`
    endpoint into the `Catalog`. Exit: one-shot bootstrap into a running engine against
    the DHIS2 play server.

Each item above is sized to a single commit with its own tests.
